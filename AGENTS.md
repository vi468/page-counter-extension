# Page Counter — инструкции для агента

Расширение Chrome/Edge (Manifest V3) для подсчёта чего угодно на странице.
Счётчик привязан к scope: `global` / `domain` / `url` / `tab`. Счётчиков может быть несколько
одновременно, у каждого свой шаг и начальное значение. **Сборки нет** — файлы как есть.

## Правила работы с репозиторием

- **В `main` не пушить напрямую.** Работа идёт в ветке `worker/<задача>` → PR → ревью → мерж.
  Прямой push блокирует хук `.githooks/pre-push` (включается через `git config core.hooksPath .githooks`).
  Осознанный обход — только при мерже проверенного PR: `ALLOW_MAIN_PUSH=1 git push origin main`.
- **Версию в `manifest.json` не поднимаем на каждую правку.** Она нужна браузеру, а не нам, и
  меняется только при публикации в стор. Тегов и релизов не делаем вовсе: история — это PR и
  `git log`, а откат — `git revert` по коммиту или кнопка Revert у PR.
- Изменения держать в рамках поставленной задачи. Ничего не рефакторить «заодно».
- **Очередь задач — GitHub Issues.** Хотелки и планы не пишем ни в README, ни в AGENTS.md: README
  описывает то, что есть. Несделанное живёт в issue, у него там есть статус и его видно.
- Комментарии, логи и тексты для пользователя — на русском, как в остальном коде.

## Карта файлов

| Файл | Ответственность |
|------|-----------------|
| `manifest.json` | MV3-манифест: права, точки входа, хоткеи (`commands`) |
| `background.js` | Service worker: бейдж на иконке, хоткеи, клик и ПКМ по иконке, автоочистка tab-счётчиков |
| `lib/storage.js` | Обёртки над `chrome.storage.local`, модель Counter, логика scope |
| `popup/` | Попап: счётчики, релевантные текущей странице |
| `options/` | Настройки, менеджер всех счётчиков, экспорт и импорт JSON |
| `tests/` | `node --test` на моке `chrome` |
| `icons/` | 16/48/128 PNG + исходный SVG |

## Модель данных

В `chrome.storage.local` два ключа: `counters` (массив) и `settings` (объект).

Счётчик: `{ id, name, value, initialValue, step, scope, isPrimary, createdAt, updatedAt }`.

`scope` — один из:

- `{ type: 'global' }`
- `{ type: 'domain', domain }` — hostname
- `{ type: 'url', url }` — origin + path + search
- `{ type: 'tab', tabId }`

Что важно знать про поведение:

- **Значения целые и неотрицательные.** Счётчик считает действия: дробных значений и шагов не
  бывает, ниже нуля он не опускается. Правила живут в `lib/storage.js` (`toInteger`,
  `normalizeValue`, `normalizeStep`, `normalizeCounterNumbers`), и любое место, которое меняет
  значение или шаг, обязано прогонять число через них — а не полагаться на то, что «и так целое».
- **Шаг — свойство счётчика, по умолчанию 1.** У каждого счётчика свой `step`, задаётся в его меню
  в попапе. Этим шагом шагают все способы: кнопки плюс/минус в попапе и менеджере, хоткеи
  `Alt+↑`/`Alt+↓` и клик по иконке. Настройки расширения шаг не задают. Автосозданный кликом по
  иконке счётчик получает шаг 1 и значение 1 — первый клик по странице без счётчика даёт 1.
- **Релевантность контексту** (`isCounterRelevant`): `global` подходит всегда, остальные — по
  совпадению домена, URL или id вкладки. Попап и бейдж работают только с релевантными.
- **Главный счётчик один на контекст** (`getPrimaryCounter`): `isPrimary` среди релевантных, иначе
  первый релевантный. Именно его значение показывается на иконке.
- **Tab-scoped счётчики удаляются при закрытии вкладки** (`pruneTabCounters` в `background.js`).
  Это не утечка, а смысл scope `tab`.
- Импорт JSON **заменяет** `counters` целиком. Записи проходят через `sanitizeCounters`: битые
  отбрасываются, дубли id тоже, число пропущенных показывается человеку.

## Архитектурные правила

- **Всё состояние — в `chrome.storage.local`.** MV3-воркер выгружается в любой момент, глобальные
  переменные между пробуждениями не живут. Исключение — флаги вроде `contextMenuReady`: они
  осознанно живут ровно одну жизнь воркера.
- **Все `addListener` — на верхнем уровне модуля.** Обработчик, зарегистрированный после `await`,
  теряется при пробуждении воркера, и событие пропадает молча.
- **`chrome.contextMenus.create` не идемпотентен.** Повторный вызов с тем же id даёт
  `Cannot create item with duplicate id` в списке ошибок расширения. Меню живут в браузере, а не
  в воркере, поэтому регистрировать их надо ровно один раз за жизнь воркера и обязательно после
  колбэка `removeAll`. `onInstalled` и `onStartup` приходят в одном жизненном цикле — именно это
  ловит регрессионный тест `tests/context-menu.test.js`.
- **Promise-формы у `chrome.contextMenus` не используем** — они доступны только с Chrome 123+.
  Только колбэки.
- **Модули, а не глобальные скрипты.** `background.js` объявлен как ES-модуль; попап и настройки
  импортируют `lib/storage.js`. У каждого относительного импорта явное расширение `.js`.
- **Сетевых запросов нет, `host_permissions` нет.** Расширение не читает содержимое страниц —
  контент-скриптов в нём нет и не планируется. Счётчик работает со своими данными, а не со
  страницей; внедряться в сайт — вне рамок проекта, даже когда задача выглядит как «всего лишь
  виджет» или «всего лишь селектор».
- **Изменения счётчиков идут только через `mutateCounters`** (`lib/storage.js`): мутация получает
  актуальный массив в момент записи, а не копию, снятую экраном раньше, и сериализуется очередью
  внутри контекста. Своя копия массива допустима только для отрисовки. Прямая `saveCounters` из
  UI — это потеря чужих изменений: попап, державший копию в памяти, затирал всё, что успело
  измениться у воркера. Атомарности между контекстами `chrome.storage.local` не даёт, поэтому щель
  сокращена до момента записи, но не закрыта полностью.

## Проверка перед сдачей задачи

1. `npm test` из корня репозитория — зелёный.
2. На баг — регрессионный тест. Проверить, что он **падает на старом коде**: временно вернуть
   прежнее поведение (например, `git stash` правки), увидеть красный, вернуть исправление.
   Зелёный тест, который не падал до правки, ничего не доказывает.
3. `node --check <файл>` для каждого правленого `.js`.
4. Проверку в живом браузере делает человек: расширение грузится распакованным в `chrome://extensions`,
   после правок — кнопка 🔄 на карточке. Тесты работают на моке `chrome` и браузерное поведение
   не воспроизводят.
5. В отчёте указать: какие файлы изменены, что именно проверено и каким способом, что осталось
   непроверенным.

## Грабли

- **`node --test tests/` на Node 24 падает** с `MODULE_NOT_FOUND`: позиционный аргумент-директория
  больше не разворачивается. Запускать `npm test` — это `node --test` без аргументов, с автопоиском.
- Мок `chrome` подставляется в `globalThis` **до** динамического `await import('../background.js')`,
  иначе воркер падает на первом же обращении к `chrome`.
- Мок `contextMenus.removeAll` вызывает колбэк синхронно: тест проверяет количество и порядок
  вызовов, но не асинхронность реального API.
- Попап может открыться без активной вкладки (мок `chrome` это воспроизводит: `tabs: []`).
  В этом состоянии `init()` обязан загрузить настройки до проверки вкладки и скрыть создание
  счётчика, а `ctx` остаётся `null` — поэтому `isCounterRelevant` возвращает false, когда контекста
  нет. Ловят `tests/popup-no-tab.test.js` и `tests/counter-resilience.test.js`.
- Данные из импорта или из старой версии могут содержать дробные и отрицательные числа. Они
  приводятся к правилам **на входе** — при импорте (`normalizeCounterNumbers`) и при любом
  изменении (`normalizeValue`), — а не на отрисовке. Не добавлять нормализацию в вёрстку.
- Счётчика без валидного `scope` не существует: `isCounterRelevant` и `pruneTabCounters` должны
  возвращать для него false, а не падать. Форма scope проверяется одной функцией `isValidScope`,
  она же отсекает мусор при импорте. Любой новый код, который читает `counter.scope`, обязан
  сперва спросить `isValidScope` — иначе он воспроизведёт падение, которое уже ловили.
- **На странице настроек модальных окон быть не должно.** `options_ui` открывается встроенной в
  `chrome://extensions`, то есть в кросс-доменном iframe, где Chrome глушит `confirm`, `prompt` и
  `alert`: `confirm` принудительно возвращает false, `prompt` — null, `alert` не показывается.
  Поэтому в `options/` запрещены любые `confirm`/`prompt`/`alert`; подтверждения и ввод делаются
  инлайн, результат показывается текстом. Любая правка менеджера счётчиков обязана проверяться
  тестом с заведомо запрещёнными диалогами (см. `tests/options-no-dialogs.test.js`). В попапе
  диалоги работают — там это правило не действует.
